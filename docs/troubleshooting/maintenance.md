# Обслуживание

Плановое обслуживание обычно сводится к обновлению образов, проверке миграций, логов и резервных копий. Подробная инструкция по автоматическим ZIP-бэкапам и восстановлению вынесена в [бэкапы и восстановление](../features/backups.md).

## Обновление из админки

На дашборде Minishop проверяет, что образы frontend, backend и worker для текущего
`IMAGE_TAG` опубликованы с одной ревизией. Для `latest` это стабильная сборка, для `dev` — сборка
ветки разработки. Номер версии оставляет установку на выбранном теге.
В окне **Обновления Minishop** можно проверить другой тег и подтвердить установку.
До подтверждения тег установки сохраняется. Локальные и сторонние сборки исключены
из автоматической проверки.

Worker проверяет публикацию каждые 15 минут. При включённых уведомлениях администраторы
и владелец с привязанным Telegram получают одно сообщение о новой ревизии. В канале
`dev` Telegram-уведомления по умолчанию выключены. Плашка на дашборде появляется
при наличии обновления независимо от этого переключателя.

Сборки со встроенным пакетом расширений проверяют публичный канал `dev` или
`latest` базового Core. Эта проверка сообщает о публикации Core. Саму сборку
обновляйте обычным для неё способом.

### Подключение кнопки установки

Один раз подключите службу на Linux-хосте с Python 3.10+, systemd и Docker
Compose v2 с поддержкой `--wait`. Она обслуживает один локальный проект с
`docker-compose.yml`, `.env`, Redis и официальными образами frontend, backend,
worker и migrate. Разнесённые по хостам сервисы обновляйте отдельно.

Нажмите **Проверить обновления** в шапке дашборда или откройте
`/admin/stats/updater`. Если служба недоступна, нажмите **Копировать команду**
в блоке установки. Выполните команду на Docker-хосте. Скрипт ищет запущенный
Minishop сначала в текущей папке и её родителях, затем среди запущенных
Core-инсталляций. Если выбор неоднозначен, передайте `--directory PATH`.
Команда из админки передаёт канал установленного магазина. Можно указать
`--channel dev` или `--channel latest` вручную. Файлы службы берутся из веток
`dev` и `main` соответственно. Пока скрипт не опубликован в `main`, доступна
установка службы из `dev`.

Для загрузки скрипта нужен `curl` или `wget`. Установщик добавляет недостающие
пакеты через APT или DNF и оставляет подходящий Python 3.10+ без обновления.
Если системный репозиторий не предлагает подходящую версию, установите её
перед повторным запуском. Docker должен уже обслуживать запущенный Minishop.

Через несколько секунд нажмите **Проверить подключение**. После подключения
кнопка **Начать обновление** становится доступна для проверенного тега
с другой ревизией или при переходе на другой тег. Администратор отдельно
подтверждает запуск. Если служба уже установлена, проверьте
`sudo systemctl status minishop-updater` и `sudo journalctl -u minishop-updater -n 50`.
Проверка образов и Telegram-уведомления доступны независимо от службы.

Штатный Compose и одноузловые профили установщика сохраняют исходные YAML,
каталог данных и режим резервного копирования. Для профилей с `./data` нужны
Docker API 1.45+ и поддержка `volume.subpath` в Compose. При запуске служба
монтирует существующий подкаталог `data` через локальный Docker-том.
Backend и worker должны использовать одну базу и один `REDIS_KEY_PREFIX`
в локальном сервисе `redis`. Учитываются порт и номер базы из `REDIS_URL`.
Для внешнего Redis, TLS, Redis с паролем, нескольких Compose-файлов
или нескольких хостов используйте обычный процесс обновления своей установки.

Служба хранит согласованную конфигурацию, включая секреты окружения, в закрытом
каталоге `/var/lib/minishop-updater`. После ручного изменения Compose или `.env`
остановите службу, повторите `--enroll` и запустите службу. Новая ревизия
проверяется для каждой роли до запуска миграций. После успешного запуска
сервисов служба записывает выбранный тег в `.env`. На время перезапуска
админка может потерять соединение, затем продолжит показывать состояние.

Чтобы отключить установку из админки, выполните
`sudo systemctl disable --now minishop-updater` после завершения текущего задания.
В течение 30 секунд дашборд снова предложит подключить службу.

Перед переходом на другую версию создайте резервную копию. При сбое проверьте
`journalctl -u minishop-updater`, `docker compose ps -a` и `docker compose logs migrate`.
Уже выполненные миграции сохраняются. При переходе на старую версию без
поддержки обновлений проверьте результат на хосте.

## Режим обслуживания пользователей

Если Remnawave недоступна или запланированы работы, откройте в админке
**Система → Настройки → Общие**, включите **Режим обслуживания**
и сохраните изменения. Настройка применяется без перезапуска. По умолчанию
`MAINTENANCE_MODE_ENABLED=False`; её также можно задать в `.env`, но сохранённое
переопределение из админки имеет приоритет.

Пользователи Telegram-бота получают сообщение о работах с просьбой попробовать
позже. Mini App показывает экран обслуживания с кнопкой повторной попытки,
а пользовательские API возвращают `503` с кодом `maintenance_mode`.
Администраторы сохраняют доступ к приложению и настройкам. Уведомления
платёжных провайдеров и проверка уже созданных платежей продолжают обрабатываться.

Ручной переключатель действует независимо от автоматики: после плановых работ
выключите его и сохраните настройки.

### Автоматическое обслуживание при недоступности панели

В том же разделе можно включить **Автообслуживание при недоступности панели**
(`MAINTENANCE_MODE_AUTO_ENABLED`). По умолчанию функция выключена. Задержка
`MAINTENANCE_MODE_AUTO_DELAY_SECONDS` задаёт минимальное время непрерывно
наблюдаемой недоступности; значение по умолчанию — 60 секунд, допустимо от 0
до 86400. Ноль включает режим после первой неудачной проверки.

Worker напрямую проверяет API панели каждые 15 секунд. Краткий сбой, завершившийся
до истечения задержки, не закрывает приложение. Когда задержка истекла,
Telegram-бот и Mini App используют тот же экран и ограничения обслуживания,
что при ручном включении. Доступ администраторов, уведомления провайдеров
и обработка уже начатых платежей сохраняются.

Первый успешный ответ панели снимает только автоматическое ограничение.
Ручной `MAINTENANCE_MODE_ENABLED` не изменяется. Администраторы с привязанным
Telegram получают уведомления о включении автоматического режима и восстановлении
панели; постоянный сбой не создаёт повторное уведомление на каждой проверке.
Без настроенного Telegram контроль панели продолжает работать без уведомлений.

Настройки применяются без перезапуска. Для проверки нужен работающий worker;
его состояние хранится в общей БД. Если проверки прекратились более чем на
90 секунд, устаревшее автоматическое ограничение перестаёт действовать.
Ручной режим при этом сохраняется. При возобновлении проверок отсчёт длительного
неподтверждённого сбоя начинается заново. В режиме `dry_run` и без адреса панели
автоматика не включается. Выключение функции сразу снимает автоматическое
ограничение, а служебное состояние очищается на ближайшей проверке worker.

## Обновление

```bash
docker compose pull
docker compose up -d
docker compose logs -f migrate backend worker
```

## Место на диске и системный журнал

В новых Compose-профилях журналы контейнеров ротируются автоматически:
три файла по 10 МБ на контейнер. Настройки и область действия описаны в
[разделе деплоя](../getting-started/deployment.md#ротация-журналов-контейнеров).

Периодически проверяйте свободное место и размер системного журнала:

```bash
df -h /
sudo journalctl --disk-usage
```

На небольшом сервере с systemd администратор может отдельно ограничить
`journald`. Следующий пример действует на **весь сервер**, включая другие
приложения; установщик Minishop не меняет эту системную настройку:

```bash
sudo mkdir -p /etc/systemd/journald.conf.d
sudo tee /etc/systemd/journald.conf.d/50-minishop-limits.conf >/dev/null <<'EOF'
[Journal]
SystemMaxUse=256M
RuntimeMaxUse=64M
SystemKeepFree=1G
EOF
sudo systemctl restart systemd-journald
```

Лимиты журналов не освобождают место, занятое базой данных, резервными копиями
или Docker-образами. Не удаляйте volumes и не обнуляйте управляемые Docker
файлы журналов вручную во время работы контейнеров.

## Резервная копия PostgreSQL

```bash
docker compose exec -T postgres sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB"' > backup.sql
```

## Автоматические бэкапы

Worker может собирать ZIP-архивы с дампом PostgreSQL и snapshot compose-папки, отправлять их в Telegram и хранить последние архивы в `data/backups`. Настройка и восстановление описаны в [отдельном разделе](../features/backups.md).

После изменения backup-настроек в `.env` перезапустите backend и worker:

```bash
docker compose up -d --build backend worker
docker compose logs -f backend worker
```

Восстановление из архива доступно в админке **Система -> Бэкапы**. Там же можно загрузить ZIP вручную, выбрать `БД` и/или `compose-папка`, а backend проверит архив перед запуском. Подробности: [бэкапы и восстановление](../features/backups.md#восстановление-из-админки).

## Проверки после работ

- `docker compose ps`
- `docker compose logs -f backend worker frontend`
- `/healthz` на backend-домене
- вход в Mini App и админку
- тестовый платеж или тестовая активация
