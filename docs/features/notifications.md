# Уведомления

Minishop отправляет уведомления в Telegram и на email. Telegram-канал означает личные сообщения пользователю с подтверждённой Telegram-привязкой, администраторам с ролью аккаунта или сообщения в `LOG_CHAT_ID` — зависит от события. Email работает при настроенном SMTP и наличии адреса у получателя.

Для автоматических пользовательских строк каналы настраиваются в **Система -> Настройки ->
Уведомления -> Доставка пользователям**. У каждой категории есть отдельные флажки Telegram и
email. Два выключенных флажка полностью запрещают уведомления этой категории.

Переключатель резервного канала разрешает доставку через единственный привязанный канал, когда
выбранный канал пользователю недоступен. Например, email-only пользователь получит письмо при
выбранном только Telegram. Если выбранный канал доступен, выключенный канал не используется.
Временный сбой отправки также не включает резервный канал.

Заблокированным пользователям автоматические уведомления не отправляются ни в Telegram,
ни по email, в том числе через резервный канал. Пропуск не записывается как успешная доставка.

Все HTML-письма используют общий email-шаблон с брендом из Web App: заголовком, accent-цветом и логотипом. Логотип, загруженный через раздел **Внешний вид**, отправляется как inline image, а публичный HTTPS-логотип остается внешней картинкой.

## Важно про окончание подписки

Если у категории включены оба канала, пользователь с привязанными Telegram и подтверждённым
адресом уведомлений получает оба
сообщения. Если доступен один канал, сообщение уходит только в него. При выключенных обоих каналах
сообщение не отправляется независимо от настройки резервного канала.

Кнопка в email-уведомлениях об окончании подписки открывает Web App через вход по email-коду: код отправляется сразу, после подтверждения пользователь попадает к продлению подписки. Для бывшей платной подписки выбирается тот же тариф, для trial - стандартный, тариф по умолчанию или первый доступный тариф.

Остальные полезные пользовательские события - успешные и неуспешные оплаты, докупки трафика/HWID, платное повышение тарифа, реферальные бонусы, предупреждения по трафику и привязка способа оплаты - тоже отправляются на выбранный email для уведомлений, если SMTP настроен. Админские email-рассылки используют тот же выбранный адрес; прямые Telegram-сообщения остаются отдельным каналом.

## Пользовательские предпочтения

В **Личном кабинете → Настройки → Уведомления** пользователь независимо управляет четырьмя
переключателями: рекламные и системные уведомления по email и в Telegram. Для новых и уже
существующих пользователей все четыре значения включены по умолчанию. Глобальные настройки
администратора остаются верхней границей: пользовательский opt-in не может включить канал,
отключённый для всей установки.

К рекламным относятся ручные рассылки администратора и автоматические кампании, использующие
публичный Core DAL получателей рассылки. К системным относятся платежи, окончание и продление
подписки, трафик, устройства, лимиты и реферальные начисления. Личные сообщения из карточки
пользователя, вход и безопасность аккаунта, а также переписка с поддержкой не считаются
рассылкой и продолжают работать.

В карточке пользователя администратор видит состояние всех четырёх переключателей и может менять
их вручную. Выключенный или физически недоступный канал считается штатным пропуском, а не ошибкой
рассылки: worker продолжает обработку остальных получателей. Автоматические кампании должны
получать аудиторию через публичный Core DAL рассылок, который уже исключает пользователей,
отключивших соответствующий рекламный канал.

Внизу рекламных и системных писем есть подписанная ссылка управления email-уведомлениями. Страница
открывается без входа, но ссылка привязана к пользователю и текущему адресу для уведомлений. После
смены адреса старая ссылка перестаёт действовать, а выбранные значения сохраняются и применяются к
новому адресу. При объединении аккаунтов выключенное значение имеет приоритет над включённым,
поэтому объединение никогда не включает ранее отключённый канал.

### Кнопка перехода к настройкам

В редакторе кнопок рассылки или личного сообщения выберите тип **Экран веб-приложения** и экран
**Настройки уведомлений**. Получатель увидит локализованную кнопку, которая откроет Mini App сразу
на `/settings/notifications`; для Telegram deep link используется безопасный параметр
`startapp=notifications`. Та же цель доступна в редакторе пользовательских кнопок меню в
**Система → Настройки → Кнопки меню**. Для каждой пользовательской кнопки отдельно задаётся
видимость в меню Telegram-бота, Telegram Mini App и обычном браузере.

Для пользовательских email-уведомлений нужен настроенный SMTP-контур и выбранный подтверждённый
адрес. Он настраивается в **Настройки → Безопасность → Почта для уведомлений** и не меняется от
способа последнего входа. Уведомления жизненного цикла подписки дополнительно требуют
`SUBSCRIPTION_EMAIL_NOTIFICATIONS_ENABLED=True`; support-уведомления администраторам дополнительно
управляются `SUPPORT_ADMIN_EMAIL_NOTIFICATIONS_ENABLED`. Подробнее: [способы входа и адреса](login-methods.md).

Администратор может полностью скрыть пользовательские настройки уведомлений через
`USER_NOTIFICATION_PREFERENCES_ENABLED=False`. В этом режиме раздел пропадает из ЛК, ссылки
управления уведомлениями не добавляются в новые письма, а публичные endpoint'ы предпочтений
возвращают `404`.

## HWID-устройства

Уведомления о новых устройствах используют отдельное событие Remnawave
`user_hwid_devices.added`, поэтому MiniShop не опрашивает список устройств всех пользователей в
фоне. Повтор одного webhook дедуплицируется по непрозрачному HMAC-отпечатку устройства; исходный
HWID, request IP и User-Agent не попадают в очередь, логи, доменные события или текст сообщения.

Категории «Новые устройства» и «Лимит устройств» имеют независимые флажки Telegram/email. Если
добавление устройства одновременно занимает последнее место и обе категории разрешены в одном
канале, пользователь получает одно объединённое сообщение. При недоступности списка устройств
отправляется только безопасное уведомление о новом устройстве без предположения, что лимит
исчерпан. Для безлимитного или неизвестного лимита предупреждение о лимите не формируется.

Кнопка ведёт в раздел «Мои устройства». Предложение докупить места появляется только когда
подписка активна, текущий тариф поддерживает периодическую оплату и для него настроен хотя бы один
платный пакет HWID-устройств. Для trial, безлимитного тарифа, отключённого раздела устройств или
отсутствующих пакетов предлагается только освободить место. Событие удаления устройства отдельно
не рассылается: оно обычно инициируется самим пользователем в этом же разделе и иначе создавало бы
дублирующее уведомление.

## Синхронизация каналов

Remnawave webhook и локальный `SubscriptionNotificationWorker` используют общий сервис отправки и общую таблицу дедупликации `subscription_notifications`.

Дедупликация ведется отдельно по каналам: например, `before_3d:telegram` и `before_3d:email`. Благодаря этому сбой одного канала не блокирует второй, а повторное событие из webhook или worker не отправляет уже доставленное уведомление повторно.

Старые записи без канала, например `before_3d`, считаются Telegram-историей. Они блокируют повторное Telegram-сообщение, но не мешают отправить email после обновления.

Если webhook от Remnawave приходит по пользователю без локальной подписки, используется legacy fallback: отправляется только Telegram по `telegram_id` из payload, без email и без канальной дедупликации.

## Блокировка торрентов (Torrent Blocker)

MiniShop обрабатывает подписанный webhook `torrent_blocker.report` из Remnawave Panel 2.7+.
Уведомление отправляется только когда `actionReport.blocked=true`: отчёты без фактической
блокировки игнорируются. Пользователю показывается причина ограничения и время автоматической
разблокировки. Имя ноды, адрес назначения, inbound/outbound и остальные технические поля
`xrayReport` не сохраняются и не показываются.

Перед включением уведомлений проверьте весь контур Torrent Blocker:

- Remnawave Panel и Remnawave Node имеют версию 2.7.0 или новее, Xray-Core — 26.3.27 или новее;
- контейнер Node запущен с `NET_ADMIN`, на хосте доступны nftables и Linux kernel 5.7+;
- в inbound включён sniffing с требуемыми `destOverride`, а Torrent Blocker включён в Node Plugin;
- `WEBHOOK_URL` панели указывает на `WEBHOOK_BASE_URL` + `/webhook/panel`, а
  `PANEL_WEBHOOK_SECRET` совпадает с секретом панели;
- webhook-канал события `torrent_blocker.report` не отключён в notifications config панели.

Полный список требований и схема события приведены в
[официальной документации Remnawave Node Plugins](https://docs.rw/docs/learn/node-plugins/).

Настройки находятся в **Система -> Настройки -> Уведомления -> Torrent Blocker**:

- `TORRENT_BLOCKER_NOTIFICATIONS_ENABLED` — общий opt-in переключатель;
- `TORRENT_BLOCKER_TELEGRAM_NOTIFICATIONS_ENABLED` — отправка в Telegram;
- `TORRENT_BLOCKER_EMAIL_NOTIFICATIONS_ENABLED` — дублирование на email при настроенном SMTP;
- `TORRENT_BLOCKER_NOTIFICATION_COOLDOWN_SECONDS` — минимальная пауза между уведомлениями
  одному пользователю в одном канале; `0` отключает cooldown, но не защиту от точных дублей;
- `TORRENT_BLOCKER_NOTIFICATION_INCLUDE_IP` — добавлять заблокированный IP в текст. По
  умолчанию выключено для приватности.

Шаблоны Telegram и email доступны в **Система -> Переводы -> Уведомления Torrent Blocker**.
MiniShop не вызывает `DELETE /api/node-plugins/torrent-blocker/truncate`: отчёты остаются в
Remnawave для админской статистики и других интеграций.

Webhook валидируется по официальному `scope=torrent_blocker` и типизированной схеме. События,
доставленные после `willUnblockAt`, считаются устаревшими и не отправляются пользователю.
Успешная доставка фиксируется отдельно для каждого канала: если Telegram уже отправлен, а SMTP
временно недоступен, retry очереди повторит только email. В логах worker публикуется метрика
`torrent_blocker_notification_total` с каналом и результатом без исходного IP-адреса.

## Служебные события Telegram и обязательный канал

`my_chat_member` в личном чате обновляет существующий статус доставки: блокировка —
`blocked`, переход из `kicked` в `member` — `enabled`. Получатель определяется по
ID личного чата, а участник `chat_member` — по `new_chat_member.user.id`, независимо
от администратора, инициировавшего изменение. Неизвестные аккаунты не создаются.
Служебные события проходят транзакцию БД, обходя пользовательские ограничения,
антифлуд, maintenance, регистрацию, синхронизацию профиля и журнал действий.
Бан магазина, роли, предпочтения уведомлений и оплаченные услуги не меняются.

Для `REQUIRED_CHANNEL_ID` членами считаются `creator`, `administrator`, `member`
и только `restricted` с `is_member=True`. Подтверждение связано с конкретным ID
канала. `REQUIRED_CHANNEL_VERIFICATION_TTL_SECONDS` задаёт срок доверия, по умолчанию
900 секунд (от 5 до 86400). Просроченное состояние проверяется на следующем
защищённом действии; полный обход базы при запуске не выполняется. Кнопка
«Проверить» обходит сохранённое подтверждение, но API-результат одной проверки
переиспользуется пять секунд, включая одновременные запросы. Этот короткий кеш
ограничен 4096 записями на процесс; межпроцессная запись остаётся атомарной в БД.
Смена канала требует нового подтверждения. Администраторы магазина сохраняют
существующее исключение из требования подписки.

Отсутствие прав, сетевой сбой и любой неопределённый ответ API означают «не удалось
проверить», а не выход пользователя. Защищённое действие остаётся неподтверждённым,
с локализованным ответом и возможностью повторить проверку. Это не отзывает
подписку Remnawave, подарок, баланс или доступ по email. В настройках рядом с ID
канала показаны права бота и время проверки. Проверка прав кешируется до 60 секунд;
изменение настроек и события прав бота требуют свежей проверки. Изменения прав
внутри статуса `administrator` также вызывают запрос. Уведомления получают
не заблокированные владельцы и администраторы с Telegram-привязкой: только при
изменении состояния и не чаще раза в пять минут на процесс.

### Порядок наблюдений и границы восстановления

`*_checked_at` — время события или начала API-попытки, а не окончания callback.
Условный SQL UPDATE принимает только более свежее наблюдение. При равном времени
служебные события упорядочены по `update_id`; идентификаторы не сравниваются между
разными датами, поэтому недельный сброс Telegram не блокирует новые события.
При равном времени локальных проверок отказ имеет приоритет над разрешением.
Точность Telegram — секунды, локальных проверок — микросекунды: проверка,
начатая внутри той же секунды, имеет приоритет над событием с началом этой секунды.
Повтор не меняет дату фактической блокировки. Поля порядка добавляет миграция
`0108_telegram_observations`.

Успешное личное входящее сообщение и завершённая отправка рассылки подтверждают
доступность с той же защитой порядка. Получение сведений через `getChat` не
доказывает возможность отправки. Настройка исключения `blocked` из новых рассылок
сохраняет выбор администратора; уже подготовленная доставка может завершиться
ошибкой после блокировки. Разблокировка не означает согласия на рассылки.

Список `allowed_updates` вычисляется из зарегистрированных роутеров: к прежним
типам, включая платежи и inline, добавлены `my_chat_member` и `chat_member`.
HTTP-вход сохраняет проверку webhook secret. `SecureSimpleRequestHandler` использует
фоновую обработку aiogram: HTTP-подтверждение может предшествовать commit, поэтому
доставка без потерь не гарантируется и внешняя очередь webhook не считается
очередью Telegram. `drop_pending_updates=True` пока сохранён: общая защита старых
пользовательских команд от повторного исполнения отсутствует, хотя платёжные
обработчики имеют отдельную идемпотентность. Перенастройка webhook теряет ожидающие
события. Переход к сохранению pending updates требует отдельного покрытия команд
и надёжного подтверждения после commit; ленивое восстановление обязательно.

### Измерения

Структурированные записи `metric` публикуют `telegram_service_updates_total`
с `kind`, `result` и задержкой `lag_seconds`, `telegram_service_write_errors_total`,
`telegram_delivery_attempts_total`, `telegram_delivery_errors_total`,
`telegram_get_chat_member_total` и `telegram_membership_active_users_total`.
Последняя считает уникальные активные аккаунты в окне 15 минут на процесс,
с пределом 10000 записей; отношение запросов к этому счётчику оценивает нагрузку
проверок. При проверке прав из админки или события публикуется
`telegram_known_blocked_fraction` среди связанных аккаунтов с известным статусом.
Telegram ID не используется как label метрик. При ошибке записи событие откатывает
транзакцию; запись о принятом наблюдении не обещает доставку при аварии процесса.
