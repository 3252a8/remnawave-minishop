# Жизненный цикл подписки



Страница описывает эксплуатационные переходы подписки после покупки: предупреждения, автопродление, trial, бонусы и привязку существующих пользователей панели.



## Предупреждения и исчерпание трафика

Remnawave ограничивает доступ при достижении `trafficLimitBytes`, переводя пользователя в статус `LIMITED`. Бот не удаляет пользователя из Internal Squads при 100% использования трафика.

`TariffTrafficWorker` запускается, когда активен JSON-каталог тарифов. Раз в 300 секунд он:

- синхронизирует из панели `status`, `trafficLimitBytes`, `usedTrafficBytes` и `trafficLimitStrategy`;
- для period-тарифов использует `trafficLimitStrategy` из Remnawave, а стратегию тарифа и затем `USER_TRAFFIC_STRATEGY` применяет как fallback, если панель не вернула стратегию;
- отправляет предупреждения на уровнях из `TARIFF_TRAFFIC_WARNING_LEVELS` (по умолчанию `85,90,95`);
- дедуплицирует предупреждения через `traffic_warnings`.

Для period-тарифов дедупликация предупреждений привязана к началу текущего периода по стратегии из Remnawave с fallback на стратегию тарифа и `USER_TRAFFIC_STRATEGY`; уведомления о сбросе отправляются только когда эффективная стратегия сброса не `NO_RESET`. Для traffic-тарифов дедупликация учитывает текущий `trafficLimitBytes`, чтобы после покупки очередного пакета пользователь мог получить следующий набор предупреждений.

Подписки, которые были ограничены логикой предыдущих запусков бота (`is_throttled=True`), восстанавливаются воркером только когда лимит снова больше использованного трафика.

## Автопродление, пробный период и бонусы

Автопродление через YooKassa применяется к подпискам на срок. Для режима продажи трафика без JSON-каталога автопродление пропускается. Для traffic-тарифов JSON-каталога покупка является пакетом трафика, а не периодической подпиской.

Пробный период использует настройки `TRIAL_DURATION_DAYS`, `TRIAL_TRAFFIC_LIMIT_GB`, `TRIAL_HWID_DEVICE_LIMIT`, `TRIAL_TRAFFIC_STRATEGY` и `TRIAL_SQUAD_UUIDS`. Он не выбирает тариф из JSON-каталога, но его можно настроить на странице **Система → Тарифы** рядом с каталогом продаж. `TRIAL_HWID_DEVICE_LIMIT` задаёт лимит устройств: пустое значение сохраняет лимит панели или значение по умолчанию, `0` означает безлимит. Докупка устройств во время trial недоступна; после исчерпания конечного лимита Web App предлагает перейти на тариф, только если хотя бы в одном доступном тарифе настроены пакеты устройств. Если `TRIAL_SQUAD_UUIDS` пустой, для trial применяются squads из `USER_SQUAD_UUIDS`; premium-сквады из тарифного каталога в обычном списке trial не выдаются как обычный доступ. Premium-доступ для trial включается отдельно через `TRIAL_PREMIUM_SQUAD_UUIDS`; если список пустой, premium-сквады не выдаются. Отдельный лимит задаёт `TRIAL_PREMIUM_TRAFFIC_LIMIT_GB`, где `0` означает доступ без отдельного premium-ограничения, а его период следует `TRIAL_TRAFFIC_STRATEGY`. Переключатель `TRIAL_WITHOUT_TELEGRAM_ENABLED` управляет активацией trial для аккаунтов без Telegram, а домены из `DISPOSABLE_EMAIL_DOMAINS` требуют привязки Telegram независимо от этого переключателя.

По умолчанию `DISPOSABLE_EMAIL_DOMAINS` содержит встроенный snapshot двух открытых списков: основной проверяемый список [disposable-email-domains](https://github.com/disposable-email-domains/disposable-email-domains) и список наиболее активных временных доменов [Castle](https://github.com/castle/disposable-email-domains). Подтверждённые дополнения, включая `prorises.com`, сохраняются отдельно и не исчезают при ротации источников. Приложение не обращается к внешним сервисам во время регистрации: snapshot обновляется отдельным скриптом, а еженедельная автоматизация предлагает изменения через PR для проверки, поэтому недоступность или ошибочное обновление источника не ломает вход пользователей.

Промокоды поддерживают несколько режимов: мгновенные бонусные дни, бонусные дни после оплаты,
скидку на checkout, множитель срока подписки и множитель выдаваемого трафика. Бонусные дни и
множитель срока работают с period-подписками; множитель трафика работает с traffic-пакетами и
докупками; скидка может применяться и к подпискам, и к traffic/HWID-покупкам. Подробности:
[промокоды](promocodes.md).

Реферальные бонусы за оплату в JSON-каталоге задаются прямо в period-тарифе рядом с ценами периода: `referral_bonus_days_inviter` для пригласившего и `referral_bonus_days_referee` для приглашенного. Ключи этих словарей - месяцы периода (`"1"`, `"3"`, `"6"`, `"12"` или любые другие периоды тарифа, например `"2"`, `"4"`, `"8"`, `"16"`). Для `traffic`-тарифов такие бонусы не применяются.

Вверху отдельного блока **Реферальная программа** на странице тарифов находится глобальный переключатель `REFERRAL_PROGRAM_ENABLED`. При выключении он прекращает обычную реферальную атрибуцию и начисление приветственных и платёжных бонусов, скрывает реферальные элементы в Telegram и Web App, а в разделе «Бонусы» оставляет только ввод промокода. Сохранённая конфигурация не удаляется, партнёрская программа работает независимо.

Приветственный бонус приглашённому (`REFERRAL_WELCOME_BONUS_DAYS`) настраивается в том же блоке. Поле каталога `referral_welcome_bonus_tariff` выбирает включённый period-тариф для новой бонусной подписки; если оно отсутствует, используется `default_tariff`. Из тарифа наследуются обычный и premium-лимиты трафика, Internal Squads, стратегия сброса и HWID-лимит. Там же флаги `REFERRAL_WEBAPP_LINK_ENABLED` и `REFERRAL_TELEGRAM_LINK_ENABLED` определяют, какие реферальные ссылки видит пользователь в разделе бонусов Web App; хотя бы один из них всегда должен оставаться включённым. `REFERRAL_WELCOME_BONUS_WITHOUT_TELEGRAM_ENABLED` разрешает или запрещает выдачу приветственного бонуса аккаунтам без Telegram; disposable email домены из `DISPOSABLE_EMAIL_DOMAINS` всегда требуют Telegram перед начислением.

Переключатель `REFERRAL_ONE_BONUS_PER_REFEREE` ограничивает платёжные реферальные бонусы первым успешным платежом приглашенного пользователя. Если он включен, повторные покупки того же приглашенного не начисляют бонусы ни ему, ни пригласившему. Приветственный бонус за регистрацию управляется отдельно и этим ограничением не отключается.

Если приглашенный покупает один тариф, а пригласивший находится на другом, размер бонуса берется из тарифа и периода, который купил приглашенный. При этом подписка пригласившего только продлевается на бонусные дни: лимиты, Internal Squads и другие параметры его текущего тарифа не пересчитываются под тариф приглашенного.

В Web App и Telegram-меню подробные строки по периодам показываются только для legacy-режима или когда активен один period-тариф. Если включено несколько period-тарифов, Web App показывает сообщение, что бонус зависит от тарифа и периода оплаты друга, затем список тарифов с диапазонами "от N до N дней" и раскрытием подробностей по иконке вопроса. Telegram-меню в этом случае показывает только диапазоны по каждому тарифу.

В legacy-режиме без JSON-каталога используются переменные `REFERRAL_BONUS_DAYS_*` и `REFEREE_BONUS_DAYS_*`; при продаже трафика без JSON-каталога Web App не показывает детализацию бонусов по месяцам. Переключатель `LEGACY_REFS` принимает старые ссылки вида `/start ref_<telegram_id>`, где payload содержит Telegram/user ID пригласившего; в админке он находится в блоке **Совместимость с legacy-тарифами**.

## Привязка существующих подписок

При запуске с активным JSON-каталогом бот выполняет безопасную сверку активных платных подписок.
Он не назначает `default_tariff` вслепую, а применяет только детерминированные соответствия:

- legacy-ключ, указанный в `legacy_keys`, приводится к каноническому ключу;
- используется тариф последнего успешного платежа подписки или смены тарифа;
- подписка без ключа получает тариф автоматически только если включён ровно один period-тариф.

Если подходящих тарифов несколько, ключ отсутствует в каталоге или у пользователя одновременно
несколько активных подписок, запись остаётся без изменений и попадает в список ручной проверки.
Результат, источник и время привязки сохраняются в `tariff_binding_source`,
`tariff_bound_at` и `tariff_binding_note`.

В админке **Система → Тарифы → Привязки подписок к тарифам** доступен dry-run с количеством
исправных, безопасно сопоставимых и неоднозначных записей. Кнопка **Применить безопасные
совпадения** изменяет только детерминированные записи; неоднозначные случаи исправляются через
карточку пользователя, где перед сменой показывается preview трафика, сквадов и HWID-лимита.
Сохранение каталога также запускает эту сверку и явно возвращает ошибку, если она не завершилась.

Новые платные активации при включённом каталоге обязаны содержать канонический `tariff_key`.
Это не позволяет снова создавать подписки, для которых недоступны тарифные функции и HWID-докупка.
