# Настройка тарифов
Бот поддерживает два способа описания продаж:

- JSON-каталог тарифов из `TARIFFS_CONFIG_PATH` (по умолчанию `data/tariffs.json`);
- конфигурация через переменные `.env`, если JSON-файл отсутствует.

JSON-каталог может содержать несколько тарифов разных моделей: подписки на срок, пакеты трафика без срока действия, разные наборы Internal Squads, лимиты устройств и пакеты докупки. Пример формата: [data/tariffs.example.json](https://github.com/3252a8/remnawave-minishop/blob/main/data/tariffs.example.json).

Важно для Docker: `TARIFFS_CONFIG_PATH` обычно указывает на файл внутри `/app/data`, и этот каталог должен быть доступен `migrate`, `backend` и `worker`. Мигратор тоже читает каталог тарифов, когда привязывает существующие активные подписки без `tariff_key` к тарифу по умолчанию и заполняет тарифные лимиты. В штатных compose-файлах это уже настроено: корневой compose использует `shop-data:/app/data`, а production-примеры - `./data:/app/data` для всех трех сервисов.

Коротко по моделям:

- `period` - подписка на срок с периодическим лимитом трафика, настраиваемым сбросом и опциональной докупкой GB поверх лимита;
- `traffic` - покупка пакетов GB без пользовательского срока действия, где повторная покупка добавляет трафик к текущему остатку;
- premium-сквады - дополнительный набор Internal Squads внутри любого тарифа, с отдельным названием, счётчиком, настраиваемым периодом лимита и отдельными пакетами докупки.

## Управление через админку

Каталог тарифов можно настраивать из Web App админки: раздел **Система → Тарифы**. Админка читает и сохраняет файл из `TARIFFS_CONFIG_PATH`, валидирует данные той же моделью `TariffsConfig`, что и бот, и атомарно перезаписывает JSON только после успешной проверки.

В интерфейсе доступны:

- добавление, редактирование и удаление тарифов;
- включение и выключение тарифа на витрине;
- выбор тарифа по умолчанию;
- настройка тарифов на срок (`period`): базовый лимит и стратегия сброса, периоды, цены в платежной валюте/Stars, реферальные бонусы и пакеты докупки трафика;
- настройка тарифов по трафику (`traffic`): пакеты GB, цены в платежной валюте/Stars, курс конвертации;
- настройка базовых Internal Squads из списка Remnawave;
- настройка premium-раздела: названия RU/EN, premium Internal Squads, лимит/безлимит и независимая стратегия сброса, пакеты докупки premium-трафика в платежной валюте/Stars;
- настройка базового HWID-лимита и пакетов докупки устройств;
- отдельные переключатели, шаги, максимумы и цены для слайдеров устройств, обычного и premium-трафика на этапе оформления подписки.

Порядок продаваемых вариантов управляется в админке перетаскиванием строк: это работает для периодов покупки подписки, traffic-пакетов, обычных докупок трафика, premium-докупок и HWID-пакетов. Такой же порядок сохраняется в JSON и затем используется в Web App и Telegram-боте.

После сохранения изменения применяются к новым запросам Web App сразу, потому что конфиг тарифов загружается из JSON при обращении. Уже созданные подписки сохраняют свой `tariff_key`; при удалении или отключении тарифа проверьте, что активные подписки с этим ключом не требуют дальнейшего продления или смены.

Подробности по админ-панели, правам доступа, сохранению настроек и списку разделов есть в [админ-панели](admin-panel.md).

## Как выбирается режим

Если файл из `TARIFFS_CONFIG_PATH` существует и проходит валидацию, используется каталог тарифов. В этом режиме `TRAFFIC_PACKAGES` и цены подписок из `.env` не формируют витрину продаж, потому что цены и пакеты берутся из JSON.

Если JSON-файл отсутствует, бот использует значения `.env`:

- `RUB_PRICE_*`, `STARS_PRICE_*` и `*_MONTHS_ENABLED` для подписок на срок;
- `TRAFFIC_PACKAGES` и `STARS_TRAFFIC_PACKAGES` для продажи пакетов трафика;
- `USER_TRAFFIC_LIMIT_GB`, `USER_TRAFFIC_STRATEGY`, `USER_SQUAD_UUIDS`, `USER_HWID_DEVICE_LIMIT` для пользователей Remnawave.

В режиме без JSON-каталога наличие `TRAFFIC_PACKAGES` или `STARS_TRAFFIC_PACKAGES` переключает витрину на продажу трафика вместо подписок на срок.

## Валюта каталога и ограничения провайдеров

JSON-каталог поддерживает `default_currency`. По умолчанию используется `rub`, поэтому существующие каталоги с `prices_rub`, `rub`-пакетами и `.env`-ценами продолжают работать без изменений. Для другой валюты укажите код в нижнем регистре, например `usd`, `eur` или `usdt`, и задайте цены в generic-полях:

- `prices`: `{ "usd": { "1": 4.99, "3": 12.99 } }`;
- `traffic_packages`, `topup_packages`, `premium_topup_packages`, `hwid_device_packages`: ключ валюты вместо `rub`, например `{ "usd": [{ "gb": 50, "price": 2.5 }] }`;
- `conversion_rate_per_gb`: курс конвертации оплаченной стоимости в GB для выбранной валюты.

Legacy-поля остаются алиасами: `prices_rub`, `conversion_rate_rub_per_gb` и ключ `rub` автоматически попадают в generic-модель. Telegram Stars остаются отдельной валютой `stars`/`XTR` и не могут быть `default_currency`.

Платежные провайдеры не принимают произвольный код валюты одинаково. Бот фильтрует способы оплаты и блокирует создание платежа, если текущая валюта каталога не поддерживается провайдером:

| Провайдер      | Валюты по умолчанию                                                                                                                                                                                                |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| YooKassa       | `RUB`                                                                                                                                                                                                              |
| WATA           | `RUB`, `USD`, `EUR`                                                                                                                                                                                                |
| FreeKassa      | `RUB`, `USD`, `EUR`, `UAH`, `KZT`                                                                                                                                                                                  |
| CryptoPay      | fiat: `USD`, `EUR`, `RUB`, `BYN`, `UAH`, `GBP`, `CNY`, `KZT`, `UZS`, `GEL`, `TRY`, `AMD`, `THB`, `INR`, `BRL`, `IDR`, `AZN`, `AED`, `PLN`, `ILS`; crypto: `USDT`, `TON`, `BTC`, `ETH`, `LTC`, `BNB`, `TRX`, `USDC` |
| Heleket        | настраиваемый список `HELEKET_SUPPORTED_CURRENCIES`                                                                                                                                                                |

## Тарифы на срок (`period`)

`period` продает доступ на срок с месячным лимитом трафика.

При покупке или продлении:

- дата начала берется от текущей активной подписки, если она еще действует, иначе от текущего времени;
- срок считается календарными месяцами через `add_months`;
- промокод может добавить бонусные дни к рассчитанному сроку;
- `tier_baseline_bytes` получает значение `monthly_gb`;
- `topup_balance_bytes` сохраняется из текущей активной подписки;
- `traffic_limit_bytes` становится `tier_baseline_bytes + topup_balance_bytes`;
- в Remnawave отправляется `trafficLimitStrategy` из тарифа с fallback на `USER_TRAFFIC_STRATEGY`;
- в Remnawave отправляются Internal Squads из тарифа;
- в Remnawave отправляется эффективный HWID-лимит тарифа.

`traffic_limit_strategy` задаётся отдельно для каждого period-тарифа. Выбранное значение применяется уже в CREATE нового пользователя Remnawave, а также при активации, продлении и смене тарифа. Если поле отсутствует в старом `tariffs.json`, сохраняется прежнее поведение через `USER_TRAFFIC_STRATEGY`; редактор показывает режим наследования, пока администратор явно не выберет стратегию. При `NO_RESET` панель не выполняет календарный сброс; `DAY`, `WEEK`, `MONTH` и `MONTH_ROLLING` задают соответствующий период. Для traffic-тарифов поле запрещено, а обычный пакет всегда использует `NO_RESET`.

В редакторе `MONTH_ROLLING` называется **«Месяц от начала подписки»**. В отличие от `MONTH`, это не календарный месяц с первого числа: месячный цикл привязан к дню начала подписки. Сводка стратегий:

| Стратегия | Граница периода | Кто ведёт обычный счётчик |
| --- | --- | --- |
| `NO_RESET` | сброса нет | Remnawave |
| `DAY` | начало каждого дня | Remnawave |
| `WEEK` | начало каждой недели | Remnawave |
| `MONTH` | первое число календарного месяца | Remnawave |
| `MONTH_ROLLING` | каждый календарный месяц от даты начала подписки | Remnawave; фактическая текущая граница приходит в `lastTrafficResetAt` |

Core передаёт Remnawave только значение `trafficLimitStrategy`: физическим сбросом обычного счётчика управляет панель. Поэтому для уже существующего пользователя источником правды остаётся возвращаемый панелью `lastTrafficResetAt`; простая смена стратегии не стирает уже учтённый трафик. Локальный `period_start_at` — кеш текущего периода для предупреждений, а не отдельный счётчик или настраиваемый якорь.

Карточка пользователя показывает фактическую стратегию из Remnawave, поэтому ручной per-user override виден сразу. Фоновые синки не заменяют его значением тарифа; следующее изменение entitlement (активация, продление или смена тарифа) снова применяет стратегию текущего тарифа.

Докупка трафика для period-тарифа увеличивает `topup_balance_bytes` и общий `traffic_limit_bytes`. Этот баланс сохраняется в подписке и учитывается при продлении period-тарифа. В панель отправляется актуальный лимит, а доступ переводится в `ACTIVE`.

## Premium-сквады и отдельный лимит

Тариф может включать дополнительный набор Internal Squads с отдельным лимитом трафика. Это удобно для сценария “обычные серверы без изменений, premium-серверы ограничены отдельно”.

```json
{
  "billing_model": "period",
  "monthly_gb": 0,
  "traffic_limit_strategy": "NO_RESET",
  "squad_uuids": ["standard-squad-uuid"],
  "premium_names": { "ru": "Premium-серверы", "en": "Premium servers" },
  "premium_squad_uuids": ["premium-squad-uuid"],
  "premium_monthly_gb": 32,
  "premium_traffic_limit_strategy": "MONTH",
  "premium_topup_packages": {
    "rub": [{ "gb": 10, "price": 99 }],
    "stars": [{ "gb": 10, "price": 2500 }]
  }
}
```

Правила:

- обычный лимит тарифа продолжает работать через `trafficLimitBytes` Remnawave;
- premium-трафик считается отдельно по нодам, доступным из `premium_squad_uuids`. На Remnawave 3.x воркер получает все ноды одним `POST /api/bandwidth-stats/nodes/usage`; на 2.8.1 используется совместимый агрегат `POST /api/bandwidth-stats/nodes/users`. По одной ноде статистика запрашивается только как fallback и для локализации продолжающегося трафика после ограничения;
- список UUID нод не хранится в тарифе: бот запрашивает accessible nodes каждого premium-сквада у Remnawave и кеширует результат;
- снимок агрегированной статистики переиспользуется до 115 секунд: это короче примерно двухминутного интервала агрегации Remnawave, поэтому частый premium-тик не повторяет заведомо одинаковые тяжёлые запросы;
- пока premium-лимит не исчерпан, пользователь получает `squad_uuids + premium_squad_uuids`;
- `squad_uuids` и `premium_squad_uuids` одного тарифа не могут содержать одинаковый UUID: иначе premium-сквад останется в базовом доступе после исчерпания лимита. Backend и редактор тарифов отклоняют такой конфликт;
- при исчерпании premium-лимита бот убирает только premium-сквады, обычный доступ остается. Изменения с одинаковым непустым итоговым набором сквадов объединяются в `POST /api/users/bulk/update-squads` (до 500 пользователей за запрос); селектор автоматически меняется с `uuids` в 2.8.1 на `userIds` в 3.x. Пустой итоговый набор применяется через per-user `PATCH /api/users`, потому что Remnawave 3.0.0 отвечает `A088/500` при попытке удалить последний сквад bulk-маршрутом. Тот же PATCH остаётся подтверждённым fallback для панели без bulk-маршрута;
- проверка premium-лимита не ждет полного тика воркера: подписки, у которых израсходовано не меньше `TARIFF_PREMIUM_FAST_WATCH_PERCENT` процентов premium-лимита (и все временно ограниченные), перепроверяются каждые `TARIFF_PREMIUM_FAST_TICK_SECONDS` секунд, поэтому перерасход ограничен минутами, а не значением `TARIFF_WORKER_TICK_SECONDS`;
- если Remnawave не отдал статистику по одной из premium-нод, использованный premium-трафик текущего периода не уменьшается: неполные данные не должны возвращать доступ пользователю сверх лимита;
- снятие сквадов останавливает только новые подключения, поэтому сразу после ограничения бот просит панель разорвать уже установленные сессии на premium-нодах. Пользователи с одинаковым набором нод объединяются в один запрос: `POST /api/ip-control/drop-connections` с `userUuids` на 2.8.1 или `POST /api/connections/drop` с `userIds` на 3.x. Обычный доступ и чужие сессии не затрагиваются. Отключается настройкой `TARIFF_PREMIUM_DROP_CONNECTIONS`, повтор ограничен `TARIFF_PREMIUM_DROP_CONNECTIONS_COOLDOWN_SECONDS`. **Для этого ноды Remnawave должны быть запущены с `CAP_NET_ADMIN`** — см. раздел ниже;
- если у уже ограниченной подписки premium-трафик продолжает расти, бот пишет warning с перечнем нод и показывает предупреждение в разделе диагностики админки;
- после докупки premium-трафика бот возвращает premium-сквады, если новый лимит снова больше использованного premium-трафика.
- докупленный premium-трафик не сгорает: сначала расходуется `premium_monthly_gb`, а докупленный остаток уменьшается только на трафик сверх базового premium-лимита;
- если `premium_traffic_limit_strategy` отсутствует или `null`, premium-учёт наследует обычную стратегию. У period-тарифа это фактический `trafficLimitStrategy` пользователя из Remnawave с fallback сначала на `traffic_limit_strategy` тарифа, затем на `USER_TRAFFIC_STRATEGY`; у traffic-тарифа наследуется его обязательный `NO_RESET`. Поэтому старые period-тарифы продолжают работать как раньше, а старые traffic-тарифы теперь последовательно наследуют отсутствие сброса обычного пакета;
- если `premium_traffic_limit_strategy` задан явно, premium-период полностью независим от обычного счётчика и per-user override в Remnawave. Например, сочетание `monthly_gb: 0`, `traffic_limit_strategy: "NO_RESET"`, `premium_monthly_gb: 32` и `premium_traffic_limit_strategy: "MONTH"` даёт безлимитный обычный трафик без сброса и отдельные 32 GB premium-трафика каждый календарный месяц;
- при `NO_RESET` premium-период идет от `start_date` подписки и не сбрасывает `premium_topup_used_bytes`; при `DAY`, `WEEK`, `MONTH` и `MONTH_ROLLING` счетчик premium-трафика и `premium_topup_used_bytes` сбрасываются на границе соответствующего периода, а `premium_topup_balance_bytes` переносится дальше. Явные `DAY`, `WEEK` и `MONTH` сразу выравниваются по календарной границе даже после смены стратегии. Явный `MONTH_ROLLING` каждый раз пересчитывается от неизменяемого `start_date` подписки и не использует даты сброса Remnawave или старый `premium_period_start_at` как новый якорь;
- `premium_period_start_at` хранит начало уже вычисленного текущего premium-периода. Это кеш окна, к которому относятся `premium_used_bytes` и `premium_topup_used_bytes`, а не дата подключения premium и не отдельная настройка тарифа;
- при переходе существующей подписки на явный premium `MONTH_ROLLING` следующий premium-тик переустанавливает окно от `start_date`. Для legacy-записи без корректного `start_date` безопасным fallback остаётся сохранённый `premium_period_start_at`; если нет и его, используется начало текущего календарного месяца;
- месяцы считаются через `add_months`: если нужного числа в следующем месяце нет, используется последний день этого месяца. Статистика premium-нод запрашивается по датам `YYYY-MM-DD`, поэтому время суток в timestamp границы не сужает окно статистики внутри дня;
- trial-подписки не используют тарифную premium-стратегию: для них, как и прежде, действует `TRIAL_TRAFFIC_STRATEGY`.

Если `premium_squad_uuids` заданы, но `premium_monthly_gb` пустой или `0`, premium-сквады не выдаются до появления положительного premium-баланса. Такой тариф можно использовать как top-up-only: при наличии `premium_topup_packages` докупка доступна сразу, без ожидания порога расходования. Для безлимитного premium-доступа задайте `premium_unlimited: true`. Если заданы `premium_topup_packages` или положительный `premium_monthly_gb`, `premium_squad_uuids` обязательны.

Состояние хранится в подписке:

- `premium_baseline_bytes` - базовый premium-лимит тарифа;
- `premium_topup_balance_bytes` - оставшийся докупленный premium-трафик;
- `premium_topup_used_bytes` - часть докупленного premium-трафика, уже потраченная в текущем premium-периоде;
- `premium_used_bytes` - использованный premium-трафик за текущий premium-период;
- `premium_period_start_at` - начало premium-периода, к которому относится `premium_used_bytes`;
- `premium_is_limited` - признак, что premium-сквад временно снят.

В пользовательском Web App premium-лимит показывается отдельной карточкой: использовано, лимит, остаток, докупленный переносимый остаток и список серверов/сквадов, на которые действует отдельное ограничение. В Telegram-разделе “Моя подписка” выводится тот же блок.

Обычная докупка и premium-докупка показываются отдельно. Обычная докупка использует `topup_packages` у `period`-тарифа или `traffic_packages` у `traffic`-тарифа. Premium-докупка использует только `premium_topup_packages`, получает `sale_mode=premium_topup` и в заголовке показывает `premium_names`, а не название обычной докупки.

Предупреждения по premium-лимиту отправляются отдельно от обычного трафика на тех же процентах `TARIFF_TRAFFIC_WARNING_LEVELS`. Сообщение использует название из `premium_names`, перечисляет серверы/сквады и ведет пользователя в докупку premium-трафика.

В Web App админке premium-сквады и стратегия их счётчика настраиваются на вкладке **Премиум трафик** в редакторе тарифа. Режим **«Наследовать стратегию обычного трафика»** выбран по умолчанию; явное значение делает premium-сброс независимым. Список сквадов берется из API Remnawave (`/api/admin/panel/internal-squads`), поэтому UUID обычно не нужно копировать вручную.

### Требование к нодам: CAP_NET_ADMIN

Когда premium-лимит исчерпан, бот убирает premium-сквады у пользователя в панели. Ноды после этого перестают принимать **новые** подключения, но уже установленную сессию xray сам по себе не разрывает. Разрывом занимается нода Remnawave, и только если её контейнер запущен с `CAP_NET_ADMIN`: без этой capability нода не может получить список онлайн-IP пользователя и закрыть его сокеты, поэтому клиент продолжает качать через открытое соединение уже после ограничения.

Проверить ноду можно по её логу при старте:

```bash
docker logs remnawave-node 2>&1 | grep CAP_NET_ADMIN
```

Строка `[OK] CAP_NET_ADMIN is available` означает, что всё в порядке. Строка `CAP_NET_ADMIN is not available.` означает, что разрыв сессий работать не будет. В этом случае добавьте capability в `docker-compose.yml` ноды и перезапустите её:

```yaml
services:
  remnawave-node:
    image: remnawave/node:latest
    cap_add:
      - NET_ADMIN
```

Если у ограниченной подписки premium-трафик продолжает расти, бот пишет предупреждение в лог и показывает баннер в разделе диагностики админки со списком проблемных нод. Кроме отсутствия `CAP_NET_ADMIN` причиной может быть нода, потерявшая связь с панелью (снятие до неё не доехало и применится при переподключении), пустой обычный сквад без inbound'ов или общий inbound между обычным и premium-сквадом — в последнем случае трафик на premium-ноде остается легальным, и разносить сквады по разным inbound'ам нужно на стороне панели.

## Тарифы по трафику (`traffic`)

`traffic` продает объем трафика без пользовательского срока действия.

При покупке:

- `end_date` ставится в дальнюю дату `2099-01-01 UTC`, если у активной подписки нет более поздней даты;
- `duration_months = 0`;
- `period_start_at = NULL`;
- `tier_baseline_bytes = 0`;
- `topup_balance_bytes` хранит доступный остаток трафика;
- в Remnawave отправляется `trafficLimitStrategy = NO_RESET`;
- автопродление и уведомления о скором окончании срока отключаются для такой подписки.

Очередная покупка добавляет GB к фактическому остатку:

```text
remaining = max(0, current_limit - current_used)
balance_after = remaining + purchased
limit_after = current_used + balance_after
```

Так пользователь не теряет уже оплаченный остаток, а Remnawave продолжает считать общий лимит от текущего использованного трафика.

Если докупка трафика вызывается для traffic-тарифа, она обрабатывается как покупка очередного пакета этого же traffic-тарифа.

## HWID-устройства

Тариф может задавать базовый лимит устройств и пакеты докупки:

```json
{
  "hwid_device_limit": 5,
  "hwid_device_packages": {
    "rub": [
      {
        "count": 1,
        "price": 99,
        "prices": { "1": 99, "3": 249, "6": 449, "12": 799 },
        "min_price": 20,
        "traffic_bonus_gb": 15
      }
    ],
    "stars": [
      {
        "count": 1,
        "price": 50,
        "prices": { "1": 50, "3": 130 },
        "traffic_bonus_gb": 15
      }
    ]
  }
}
```

Правила:

- пользовательский раздел и все новые HWID-счета доступны только при
  `MY_DEVICES_SECTION_ENABLED=True`;
- у пользователя должна быть активная подписка с каноническим `tariff_key`, который существует
  в текущем каталоге, включён и относится к модели `period`;
- тариф должен иметь конечный базовый лимит и хотя бы один пакет с положительной ценой в
  платежной валюте каталога или Telegram Stars;
- Web App и Telegram используют одну проверку доступности и показывают точную причину блокировки;
  перед созданием счёта сервис повторно проверяет флаг раздела, активный тариф и пакет, поэтому
  устаревшая кнопка или callback не обходят ограничения;
- `hwid_device_limit` хранит базовый лимит тарифа;
- `extra_hwid_devices` хранит только текущую активную сумму докупленных устройств;
- срок действия каждой докупки хранится в `hwid_device_purchases.valid_from` / `valid_until`;
- эффективный лимит равен `hwid_device_limit + active extra_hwid_devices`;
- `traffic_bonus_gb` — ежемесячная добавка к основному лимиту на весь пакет, а не на каждое устройство; `0` отключает бонус;
- бонус фиксируется в платеже и записи докупки, поэтому последующее редактирование тарифа не меняет уже купленное право;
- бонусы активных докупок складываются, начинают действовать в `valid_from` и исчезают после `valid_until`;
- базовый лимит `0` означает безлимит, в Remnawave отправляется `hwidDeviceLimit = 0`;
- при безлимитном базовом лимите докупка устройств не применяется;
- полная цена HWID-пакета берется из `prices[duration_months]`; если периода нет, используется fallback `price * duration_months`;
- фактическая цена докупки считается пропорционально оплачиваемому окну `valid_from -> valid_until` относительно периода подписки и фиксируется в платежe;
- для Telegram Stars цена округляется вверх до целого Stars, для платежной валюты — вверх до копеек; `min_price` защищает от микроплатежей в конце периода;
- кнопка докупки устройств всегда покупает устройства только для текущей активной подписки и только до текущего срока ее действия;
- при продлении подписки пользователь видит отдельный чекбокс продления действующих докупленных устройств; чекбокс включен по умолчанию, цена считается по текущему тарифу и добавляется в тот же платеж подписки;
- если пользователь продлил подписку без продления устройств, старая докупка продолжает действовать до своего `valid_until`, а Web App показывает предупреждение о возможном временном возврате к базовому лимиту;
- админские продления, промокоды и реферальные бонусы добавляют фиксированное количество дней отдельно к подписке и к действующим докупкам устройств, не склеивая даты окончания;
- `traffic`-тарифы не показывают и не принимают докупку HWID-устройств, потому что у них нет срока подписки;
- при смене тарифа базовый лимит берется из целевого тарифа, а неиспользованная стоимость HWID-докупок в платежной валюте конвертируется в дни нового period-тарифа или GB traffic-тарифа; XTR/Stars-докупки не конвертируются без явного курса и продолжают жить по своему `valid_until`;
- история докупок пишется в `hwid_device_purchases`;
- платеж хранит количество устройств в `payments.purchased_hwid_devices` и снимок бонуса в `payments.hwid_traffic_bonus_bytes`.

Докупка устройств доступна в Web App через `/api/devices/topup-options` и `/api/payments`, а также
в Telegram-боте из раздела устройств. Свободные места внутри базового лимита (например, занято
`1 из 5`) не влияют на видимость покупки: кнопка означает увеличение максимального лимита, а не
разблокировку текущих пяти мест.

## Платежи

В платежах используются поля:

| Поле                                                                    | Назначение                                                                                                      |
| ----------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| `sale_mode`                                                             | Тип продажи: `subscription`, `traffic_package`, `topup`, `premium_topup`, `tariff_upgrade`, `hwid_devices`.     |
| `tariff_key`                                                            | Ключ тарифа, к которому относится платеж.                                                                       |
| `purchased_gb`                                                          | Купленный объем GB для traffic-пакетов и докупки трафика.                                                       |
| `purchased_hwid_devices`                                                | Количество устройств при докупке HWID.                                                                          |
| `hwid_valid_from`, `hwid_valid_until`                                   | Зафиксированное окно действия HWID-докупки на момент создания платежа.                                          |
| `hwid_pricing_period_months`, `hwid_proration_ratio`, `hwid_full_price` | Метаданные расчета цены HWID-докупки: период тарифа, коэффициент prorate и полная цена пакета для периода.      |
| `subscription_duration_months`                                          | Количество месяцев для подписки на срок; также используется платежными обработчиками как числовое поле покупки. |
| `checkout_bundle_snapshot`, `checkout_bundle_hash`                      | Неизменяемый состав докупок при оформлении подписки и его SHA-256 для сопоставления pending-платежей.            |

В callback и metadata платежных провайдеров `sale_mode` может передаваться с суффиксом тарифа, например `subscription@standard` или `topup@standard`. При активации платежа тариф сохраняется отдельно в `tariff_key`.
