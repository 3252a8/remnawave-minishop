# Способы входа: Google, Яндекс и ключи доступа

Minishop поддерживает Telegram, email, Google, Яндекс и passkey. В админке они собраны в
**Система → Настройки → Способы входа**, а пользователь управляет привязками и адресом для
уведомлений в **Настройки → Безопасность**.

## Модель аккаунта и защита от дублей

Один пользователь Minishop может иметь несколько способов входа и несколько подтверждённых
email-адресов. При этом роли адресов разделены:

- **основной email** используется для входа по коду/паролю, восстановления доступа и синхронизации
  поля email в Remnawave Panel;
- **email для уведомлений** явно выбирается пользователем из подтверждённых адресов;
- Google и Яндекс идентифицируются стабильной парой `provider + subject`, а не адресом почты;
- дополнительный адрес OIDC не становится логином по email и не меняет запись в Remnawave Panel
  сам по себе.

Если новый вход Google или Яндекс возвращает email, уже занятый существующим аккаунтом, backend
**не создаёт второго пользователя и не связывает аккаунты только по совпавшей строке**. После
успешного OAuth backend отправляет одноразовый код на уже подтверждённый адрес. OAuth подтверждает
доступ к аккаунту провайдера, а код — владение существующим аккаунтом Minishop. Только после обеих
проверок identity привязывается к исходной записи и пользователь входит в неё. Основной email,
адрес уведомлений и поле email в Remnawave Panel при этом не меняются.

Контекст незавершённой привязки хранится в короткоживущей подписанной HttpOnly-cookie. Клиент
отправляет обратно только код: `provider`, стабильный `subject`, точный email и ID целевого
пользователя нельзя подменить в браузере. Перед повторной отправкой и подтверждением backend снова
проверяет владельца email, существующие identity и включённость провайдера. Истёкший контекст,
сменившийся владелец адреса и параллельная привязка завершаются ошибкой без создания пользователя.

При объединении сохраняются подтверждённые адреса обеих записей, но основной адрес целевого
аккаунта не меняется автоматически. Подписки, платежи, реферальные ограничения и другие сущности
проходят существующие проверки конфликтов. Если безопасное объединение невозможно, операция
останавливается без частичных изменений.

## Общие требования

Укажите публичный HTTPS URL Mini App:

```ini
SUBSCRIPTION_MINI_APP_URL=https://app.example.com/
WEBAPP_SESSION_SECRET=<stable-random-secret>
```

Маршруты `/auth/*` должны попадать в Web App API. В штатном Docker Compose они проходят через
frontend nginx. Для собственного reverse proxy не отправляйте callback в webhook-сервер на порту
`8080` — Web App backend слушает внутренний порт `8081`.

Для production используйте отдельные OAuth-приложения и секреты. Не помещайте client secret в
frontend, публичные JSON-конфиги или URL.

## Google

1. Откройте [Google Cloud Console](https://console.cloud.google.com/apis/credentials) и выберите
   отдельный production-проект.
2. Настройте OAuth consent screen: название сервиса, контакты, домен, privacy policy и terms.
3. Создайте OAuth 2.0 Client ID типа **Web application**.
4. Поле **Authorized JavaScript origins** оставьте пустым. Minishop использует серверный
   Authorization Code Flow с PKCE и не загружает Google Identity Services JavaScript SDK, поэтому
   origin браузера регистрировать не требуется.
5. В **Authorized redirect URIs** добавьте точный адрес:

```text
https://app.example.com/auth/google/callback
```

6. Перенесите значения в Minishop и включите способ входа:

```ini
GOOGLE_OIDC_ENABLED=True
GOOGLE_OIDC_CLIENT_ID=<client-id>.apps.googleusercontent.com
GOOGLE_OIDC_CLIENT_SECRET=<client-secret>
```

Minishop запрашивает только `openid email profile`, проверяет подпись и стандартные OIDC claims,
включая `iss`, `aud`, `exp`, `nonce`, и принимает email только при `email_verified=true`.

Google требует точного совпадения redirect URI, включая схему, регистр, порт, путь и завершающий
слеш. Подробности: [OAuth 2.0 for Web Server Applications](https://developers.google.com/identity/protocols/oauth2/web-server).

Настройки Google и Яндекс, сохранённые в админке, сразу применяются к следующим запросам
`/auth/{provider}/start` и `/auth/{provider}/callback`: перезапуск backend не требуется. Экран
входа и кешированные данные кабинета также обновляются после сохранения. Если админка сообщает,
что конкретный ключ «сохранён, но не применён», он не считается активным до перезапуска — это
защитный сценарий для неизвестных или неподдерживаемых параметров.

## Яндекс

1. Откройте [Yandex OAuth](https://oauth.yandex.ru/) и создайте приложение **для авторизации
   пользователей**.
2. Добавьте платформу **Веб-сервисы**.
3. Укажите Redirect URI:

```text
https://app.example.com/auth/yandex/callback
```

4. Разрешите минимальные права `login:email`, `login:info` и `login:avatar`.
5. Сохраните client ID/secret в Minishop:

```ini
YANDEX_OIDC_ENABLED=True
YANDEX_OIDC_CLIENT_ID=<client-id>
YANDEX_OIDC_CLIENT_SECRET=<client-secret>
```

Для контакта Minishop использует `default_email`, возвращённый Yandex ID. Этот адрес добавляется
как подтверждённый адрес провайдера, но не заменяет основной email существующего аккаунта без
явного действия пользователя.

Пошаговая регистрация приложения описана в
[официальной документации Yandex ID](https://yandex.com/dev/id/doc/en/register-auth).

## Ключи доступа (passkey)

Passkey работает через WebAuthn и требует HTTPS (исключение браузеров для локального `localhost`
не следует использовать как production-настройку).

```ini
PASSKEY_LOGIN_ENABLED=True
PASSKEY_RP_ID=app.example.com
PASSKEY_RP_NAME=Example VPN
PASSKEY_ORIGINS=https://app.example.com
PASSKEY_CHALLENGE_TTL_SECONDS=300
```

- `PASSKEY_RP_ID` — домен без протокола, порта и пути;
- `PASSKEY_RP_NAME` — понятное имя сервиса, которое устройство предлагает в названии нового ключа;
- `PASSKEY_ORIGINS` — полный origin с `https://`; несколько origin перечисляются через запятую;
- после смены RP ID старые ключи перестанут работать для нового домена;
- не отключайте все остальные способы входа, пока не проверили passkey на втором устройстве.

Подробнее о модели RP, регистрации и входе: [Passkeys на MDN](https://developer.mozilla.org/en-US/docs/Web/Security/Authentication/Passkeys).

## Адреса почты и уведомления

После привязки Google или Яндекса их подтверждённые адреса появляются в разделе
**Настройки → Безопасность → Почта для уведомлений**. Пользователь выбирает ровно один адрес.
Выбор сохраняется и не меняется от того, каким способом выполнен следующий вход.

Основной email меняется отдельным двухэтапным сценарием: код сначала отправляется на текущий
адрес, затем второй код — на новый. После успешной смены новый адрес становится основным и адресом
уведомлений, а Minishop синхронизирует его в поле email пользователя Remnawave Panel. Привязка или
отвязка OIDC-провайдера сама по себе поле email в Panel не меняет.

В админке смену основного адреса можно отключить независимо от входа по email:

```ini
EMAIL_ADDRESS_CHANGE_ENABLED=True
```

По умолчанию смена разрешена. При отключении кнопка в кабинете становится неактивной, а backend
отклоняет все этапы уже начатого сценария. Это не мешает пользователю привязать почту впервые,
войти по коду или паролю и выбрать другой подтверждённый OIDC-адрес для уведомлений.

Сценарий смены выполняется в одном модальном окне:

1. Minishop отправляет одноразовый код на текущий основной адрес. Код ограничен по времени,
   количеству попыток и не может быть использован повторно.
2. После проверки старого адреса пользователь вводит новый. Если адрес уже принадлежит другому
   аккаунту — как основной email или как подтверждённый адрес Google/Яндекса — операция
   останавливается до создания каких-либо новых записей.
3. Второй одноразовый код отправляется на новый адрес. Подмена адреса между запросом и
   подтверждением невозможна: код и короткоживущий токен привязаны к пользователю и адресу.
4. После второго подтверждения обновляются основной email, адрес уведомлений и поле email в
   Remnawave Panel. На старый адрес приходит уведомление безопасности, а на новый — письмо об
   успешной смене. Ошибка отправки этих информационных писем не откатывает уже подтверждённую
   смену.

Уникальность нового адреса проверяется перед отправкой кода и повторно в транзакции при
подтверждении. Ограничения базы данных закрывают гонку параллельных запросов: пользователь увидит
понятную ошибку о занятом адресе, а не частично изменённый профиль.

Коды входа, восстановления и подтверждения основного email всегда отправляются на адрес,
введённый для соответствующей операции. Автоматические уведомления о подписке, платежах, трафике,
устройствах, поддержке и админские email-рассылки идут на выбранный адрес уведомлений.

## Проверка

1. Сохраните настройки провайдера; поддерживаемые параметры применяются без перезапуска.
2. Проверьте callback URL в админке и в кабинете провайдера — они должны совпадать полностью.
3. Войдите новым Google/Яндекс-аккаунтом и убедитесь, что создана одна запись пользователя.
4. Повторите вход с адресом уже существующего email-аккаунта: Minishop должен сразу отправить код
   на этот адрес, после подтверждения привязать Google/Яндекс и не создать дубль.
5. Проверьте в «Безопасности», что provider появился у исходного аккаунта, а подписка, основной
   email, адрес уведомлений и поле email в Remnawave Panel не изменились.
6. Добавьте passkey, выйдите и войдите с ним; затем проверьте удаление ключа при наличии другого
   способа входа.
7. Выберите другой подтверждённый адрес уведомлений и отправьте тестовое уведомление.

## Частые ошибки

- `redirect_uri_mismatch`: callback отличается схемой, доменом, портом, путём или слешем.
- Кнопка провайдера скрыта: способ выключен либо client ID/secret не заполнены полностью.
- Возврат `account_exists`: совпавший основной email существует, но ещё не считается подтверждённым
  для безопасной автоматической привязки; войдите по email и привяжите провайдера в «Безопасности».
- Подтверждение OIDC устарело: повторите вход через Google/Яндекс. Контекст живёт столько же,
  сколько код; при смене владельца email, отключении провайдера или конфликте identity он
  аннулируется раньше.
- Passkey недоступен: страница открыта без HTTPS, RP ID не соответствует домену или origin не
  входит в `PASSKEY_ORIGINS`.
- Уведомления идут не туда: проверьте выбранный адрес в «Почта для уведомлений»; способ последнего
  входа на получателя не влияет.

Настройка SMTP и email-пароля описана в [разделе входа по email](email-login.md), Telegram — в
[разделе Telegram-авторизации](telegram-auth.md).
